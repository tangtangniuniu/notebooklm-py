# NAME

PAGI::Server - PAGI Reference Server Implementation

# SYNOPSIS

```
use IO::Async::Loop;
use PAGI::Server;

# If using Future::IO libraries (Async::Redis, SSE->every, etc.)
# load the IO::Async implementation BEFORE loading them:
use Future::IO::Impl::IOAsync;

my $loop = IO::Async::Loop->new;

my $server = PAGI::Server->new(
    app  => \&my_pagi_app,
    host => '127.0.0.1',
    port => 5000,
);

$loop->add($server);
$server->listen->get;  # Start accepting connections
```

See ["LOOP INTEROPERABILITY"](#LOOP-INTEROPERABILITY) for details on Future::IO configuration.

# DESCRIPTION

PAGI::Server is a reference implementation of a PAGI-compliant HTTP server. It supports HTTP/1.1, WebSocket, and Server-Sent Events (SSE) as defined in the PAGI specification. It prioritizes spec compliance and code clarity over performance optimization. It serves as the canonical reference for how PAGI servers should behave.

# PROTOCOL SUPPORT

**Currently supported:**

* HTTP/1.1 (full support including chunked encoding, trailers, keepalive)
* HTTP/2 (**experimental** - via nghttp2, h2 over TLS and h2c cleartext)
* WebSocket (RFC 6455, including over HTTP/2 via RFC 8441)
* Server-Sent Events (SSE, including over HTTP/2)

**Not yet implemented:**

* HTTP/3 (QUIC) - Under consideration

For HTTP/2, see ["ENABLING HTTP/2 SUPPORT (EXPERIMENTAL)"](#ENABLING-HTTP%2F2-SUPPORT-(EXPERIMENTAL)).

# UNIX DOMAIN SOCKET SUPPORT (EXPERIMENTAL)

**This feature is experimental.** The API is subject to change in future releases. Please report issues at <https://github.com/jjn1056/pagi/issues>.

Unix domain sockets provide efficient local communication between a reverse proxy (nginx, HAProxy, etc.) and PAGI::Server running on the same machine. They bypass the TCP/IP stack entirely, reducing latency and overhead compared to connecting over `127.0.0.1`.

## When to Use Unix Sockets

* **Behind a reverse proxy** — nginx or HAProxy on the same host handles TLS termination, HTTP/2 negotiation, and static files, forwarding dynamic requests to PAGI over a Unix socket.
* **Benchmarks** — frameworks like TechEmpower FrameworkBenchmarks use Unix sockets to eliminate network variable from application benchmarks.
* **Microservice IPC** — services on the same host communicate without network overhead.

**When NOT to use:** If clients connect over the network (remote browsers, API consumers), use TCP. Unix sockets only accept connections from processes on the same machine.

## Basic Usage

**Programmatic:**

```
my $server = PAGI::Server->new(
    app    => $app,
    socket => '/tmp/pagi.sock',
);
```

**CLI:**

```
pagi-server --socket /tmp/pagi.sock ./app.pl
```

**With workers:**

```
pagi-server --socket /tmp/pagi.sock --workers 4 ./app.pl
```

In multi-worker mode, the parent process creates the Unix socket and all worker processes inherit the file descriptor via `fork()`. The kernel distributes incoming connections across workers.

## How It Works

1. On startup, any existing file at the socket path is removed (stale socket cleanup).


2. The server creates and binds a `SOCK_STREAM` Unix domain socket at the specified path using `IO::Socket::UNIX` (multi-worker) or `IO::Async::Listener` with `family => 'unix'` (single-worker).


3. If `socket_mode` is set, `chmod()` is called immediately after binding to set the file permissions.


4. In multi-worker mode, the parent creates the socket before forking. Workers inherit the listening fd and each runs its own `IO::Async::Listener` wrapping the inherited handle.


5. On graceful shutdown (SIGTERM/SIGINT), the socket file is unlinked by both the single-worker `shutdown()` path and the multi-worker `_initiate_multiworker_shutdown()` path.

## nginx Configuration

**Basic upstream:**

```
upstream pagi_backend {
    server unix:/var/run/myapp/pagi.sock;
    keepalive 32;
}

server {
    listen 80;
    server_name myapp.example.com;

    location / {
        proxy_pass http://pagi_backend;

        # Required for upstream keepalive:
        proxy_http_version 1.1;
        proxy_set_header Connection "";

        # Forward client info (since PAGI can't see it over Unix socket):
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

**Important:** The `keepalive` directive is critical for performance. Without it, nginx opens a new Unix socket connection for every request. `proxy_http_version 1.1` and `proxy_set_header Connection ""` are required for keepalive to work.

**With TLS termination at nginx:**

```
server {
    listen 443 ssl http2;
    ssl_certificate     /etc/ssl/myapp.crt;
    ssl_certificate_key /etc/ssl/myapp.key;

    location / {
        proxy_pass http://pagi_backend;
        # ... same proxy headers as above
    }
}
```

nginx handles TLS and HTTP/2 with clients, then speaks plain HTTP/1.1 to PAGI over the Unix socket. This is the recommended production pattern.

## Socket Permissions and Security

By default, the socket file inherits permissions from the process umask. Use `socket_mode` to set explicit permissions:

```
# CLI
pagi-server --socket /var/run/myapp/pagi.sock --socket-mode 0660 ./app.pl

# Programmatic
PAGI::Server->new(
    app         => $app,
    socket      => '/var/run/myapp/pagi.sock',
    socket_mode => 0660,
);
```

**Production recommendations:**

* **Use a dedicated directory**, not `/tmp/`. Directories like `/var/run/myapp/` or `/run/myapp/` prevent symlink attacks and provide an additional permission layer.
* **Use `0660` with a shared group.** Create a group (e.g., `myapp`) that both the application user and the nginx user belong to:

  ```
  sudo groupadd myapp
  sudo usermod -aG myapp www-data    # nginx user
  sudo usermod -aG myapp myappuser   # app user
  sudo mkdir -p /var/run/myapp
  sudo chown myappuser:myapp /var/run/myapp
  sudo chmod 0750 /var/run/myapp
  ```
* **Use systemd `RuntimeDirectory`** for automatic directory management:

  ```
  # /etc/systemd/system/myapp.service
  [Service]
  User=myappuser
  Group=myapp
  RuntimeDirectory=myapp
  RuntimeDirectoryMode=0750
  ExecStart=/usr/local/bin/pagi-server \
      --socket /run/myapp/pagi.sock \
      --socket-mode 0660 \
      --workers 4 \
      /opt/myapp/app.pl
  ```

  systemd creates `/run/myapp/` on service start and cleans it up on stop.

## TLS Over Unix Sockets

TLS can be used over Unix sockets, though this is unusual — normally the reverse proxy handles TLS termination. When TLS is configured on a Unix socket listener, the server logs an info-level note suggesting reverse proxy TLS termination instead.

The combination is allowed because it has legitimate uses (encrypted inter-container communication, compliance requirements). All major ASGI servers (Uvicorn, Hypercorn, Granian) also allow it.

## HTTP/2 Over Unix Sockets

h2c (HTTP/2 cleartext) works over Unix sockets. This is useful for gRPC backends or reverse proxies that support HTTP/2 to upstreams (e.g., Envoy). Note that nginx does **not** currently support HTTP/2 to upstream backends (except for gRPC via `grpc_pass`).

## Scope Differences

For Unix socket connections, the PAGI scope differs from TCP connections:

* **`client` is absent** — Unix sockets have no peer IP address or port. The `client` key is omitted entirely from the scope hashref (not set to `undef`). This is spec-compliant: the PAGI specification marks `client` as optional.
* **`server` is `[$socket_path, undef]`**> — instead of `[$host, $port]`.

**Middleware implications:** Any middleware that accesses `$scope->{client}` must check `exists $scope->{client}` first. For client IP identification behind a reverse proxy, use `X-Forwarded-For` or `X-Real-IP` headers instead of `$scope->{client}`. The `PAGI::Middleware::XForwardedFor` middleware (if available) handles this automatically.

**Access log:** Unix socket connections log `unix` as the client IP in the access log instead of an IP address.

## Stale Socket Cleanup

If a socket file already exists at the configured path (e.g., from a previous crash), it is automatically removed before binding. This matches the behavior of Starman, Gunicorn, Uvicorn, and other production servers. The socket file is also removed during graceful shutdown (SIGTERM/SIGINT).

If the server is killed with SIGKILL (`kill -9`), the socket file will **not** be cleaned up. It will be removed on the next startup.

# MULTI-LISTENER SUPPORT (EXPERIMENTAL)

**This feature is experimental.** The API is subject to change in future releases.

A single PAGI::Server instance can listen on multiple endpoints simultaneously. This is useful for:

* **TCP for health checks + Unix socket for app traffic** — load balancers probe a TCP port while nginx uses the Unix socket.
* **Multiple TCP ports** — serve different interfaces on different ports.
* **Gradual migration** — listen on both old and new ports during a transition.

## Programmatic API

```
my $server = PAGI::Server->new(
    app    => $app,
    listen => [
        { host => '0.0.0.0', port => 8080 },
        { socket => '/tmp/pagi.sock', socket_mode => 0660 },
    ],
);
```

Each spec in the `listen` array is a hashref with either `{ host, port }` for TCP or `{ socket }` (with optional `socket_mode`) for Unix sockets.

**Note:** Per-listener TLS configuration is not yet supported. TLS is configured server-wide via the `ssl` constructor option and applies to all TCP listeners. Unix socket listeners behind a reverse proxy do not need TLS — the proxy handles TLS termination.

## CLI

The `--listen` flag is repeatable. The server auto-detects TCP vs Unix socket: values containing `:` are parsed as `host:port`, everything else is treated as a Unix socket path.

```
# TCP + Unix socket
pagi-server --listen 0.0.0.0:8080 --listen /tmp/pagi.sock ./app.pl

# Multiple TCP ports
pagi-server --listen 0.0.0.0:8080 --listen 0.0.0.0:8443 ./app.pl

# With workers
pagi-server --listen 0.0.0.0:8080 --listen /tmp/pagi.sock -w 4 ./app.pl

# IPv6
pagi-server --listen [::1]:5000 ./app.pl
```

`--listen` is **mutually exclusive** with `--host`, `--port`, and `--socket`. `--socket-mode` applies to all Unix socket listeners when using `--listen`.

## How It Works

* In **single-worker mode**, one `IO::Async::Listener` is created per endpoint. All listeners share the same event loop and connection handler.
* In **multi-worker mode**, the parent process creates all listening sockets (Unix and TCP) before forking. Workers inherit all file descriptors and create their own `IO::Async::Listener` for each inherited socket.
* The `reuseport` option applies only to TCP listeners. Unix socket listeners always use the shared-socket model (parent creates, workers inherit).
* On shutdown, all listeners are stopped and all Unix socket files are cleaned up.

## Accessors

```
$server->port;          # Bound port of first TCP listener, or undef
$server->socket_path;   # Path of first Unix socket listener, or undef
$server->listeners;     # Arrayref of all listener specs
```

## Backward Compatibility

The existing `host`/`port` constructor options continue to work exactly as before. They are internally normalized to a single-element listener array. The `socket` option is similarly sugar for a single Unix socket listener. Only `listen` enables true multi-listener mode.

# SYSTEMD SOCKET ACTIVATION (EXPERIMENTAL)

**This feature is experimental.** The API is subject to change in future releases.

PAGI::Server supports systemd socket activation, which allows systemd to create and hold listening sockets on behalf of the server. This enables zero-downtime restarts: when the server is restarted, the kernel continues to queue incoming connections on the socket without refusing or dropping them, even during the gap between the old process exiting and the new one starting.

Benefits of systemd socket activation:

* **Zero-downtime restarts** — the kernel queues connections during restarts
* **Atomic permission handling** — systemd creates the socket as root, then drops privileges before exec
* **On-demand activation** — the server is started automatically when the first connection arrives

## Basic Setup

Create two systemd unit files: a `.socket` unit that describes the socket, and a `.service` unit for the server itself.

**TCP socket (`/etc/systemd/system/pagi.socket`):**

```
[Unit]
Description=PAGI Application Socket

[Socket]
ListenStream=0.0.0.0:8080
Accept=no

[Install]
```

## How Auto-Detection Works

When PAGI::Server starts, it checks the `LISTEN_FDS` and `LISTEN_PID` environment variables set by systemd. If `LISTEN_PID` matches the current process PID, the server inspects each inherited file descriptor (starting at fd 3) with `getsockname()` to determine its address.

Each inherited socket is then matched against the configured listeners. For example, if you configure `port => 8080` and systemd has a socket bound to `0.0.0.0:8080`, PAGI::Server will use the inherited fd instead of creating a new socket.

The same application code works identically with or without systemd:

```
# Without systemd: PAGI::Server binds the socket itself
# With systemd:    PAGI::Server inherits the socket from systemd
my $server = PAGI::Server->new(
    app  => $app,
    host => '0.0.0.0',
    port => 8080,
);
```

After reading the inherited fds, PAGI::Server removes `LISTEN_FDS`, `LISTEN_PID`, and `LISTEN_FDNAMES` from the environment (per the `sd_listen_fds(3)` specification), so child processes do not re-inherit them.

## Unix Socket Cleanup

Normally, PAGI::Server unlinks its Unix socket file on shutdown. For systemd-activated Unix sockets, the socket file is **not** unlinked because systemd owns the socket and will recreate it for the next activation.

# FD REUSE INTERNALS (EXPERIMENTAL)

**This feature is experimental.** The API is subject to change in future releases.

PAGI::Server uses a `PAGI_REUSE` environment variable to pass inherited listening socket file descriptors to re-exec'd processes during hot restart (see ["HOT RESTART (EXPERIMENTAL)"](#HOT-RESTART-(EXPERIMENTAL))). This mechanism also supports systemd socket activation (see ["SYSTEMD SOCKET ACTIVATION (EXPERIMENTAL)"](#SYSTEMD-SOCKET-ACTIVATION-(EXPERIMENTAL))).

## PAGI\_REUSE Format

The variable is a comma-separated list of `addr:port:fd` entries:

```
# TCP listeners
PAGI_REUSE=127.0.0.1:8080:3,0.0.0.0:8443:4

# Unix socket listeners
PAGI_REUSE=unix:/run/pagi/app.sock:5

# Mixed
PAGI_REUSE=0.0.0.0:8080:3,unix:/run/pagi/app.sock:4
```

Each entry encodes the address the socket is bound to and the file descriptor number to use.

## Fd Matching

When starting, `_collect_inherited_fds()` parses `PAGI_REUSE` and/or `LISTEN_FDS`, building a table of `address => fd` pairs. During `listen()`, each configured listener looks up its own address in the table. If a match is found, the existing fd is used instead of calling `bind()` and `listen()`. This allows the kernel's accept queue to be preserved across restarts.

## File Descriptor Inheritance

To ensure that listening socket fds are inherited across `exec()`, PAGI::Server sets `$^F = 1023` before creating sockets. Perl uses `$^F` (the maximum system file descriptor, equivalent to `POSIX_OPEN_MAX` in spirit) to decide which fds receive the `FD_CLOEXEC` close-on-exec flag: fds with numbers greater than `$^F` get `FD_CLOEXEC` set automatically. By raising `$^F` to 1023, listen socket fds remain open across `exec()` without requiring explicit `fcntl` calls.

# HOT RESTART (EXPERIMENTAL)

**This feature is experimental.** The API and signal behaviour are subject to change in future releases.

Deploying new code normally requires a server restart. During that restart there is a gap — however brief — where the listening socket is closed and incoming connections are dropped. Hot restart eliminates this gap by having the old master fork and exec a brand-new master process that **inherits** the already-open listening sockets. Both the old master and the new master serve requests during the transition; clients never see a refused connection.

## How It Works

1. An admin sends `SIGUSR2` to the running master: `kill -USR2 <master_pid>`
2. The old master sets `PAGI_REUSE` (encoding each listening socket fd) and `PAGI_MASTER_PID` (its own PID) in the environment, then calls `fork()` followed immediately by `exec()` of the original `pagi-server` command (reconstructed from `PAGI_ARGV`).
3. The new master starts, finds the inherited file descriptors via `PAGI_REUSE`, and reuses the existing listening sockets rather than calling `bind()`/`listen()` again. The kernel's accept queue is preserved — no connections are dropped.
4. The new master spawns its worker pool and waits for each worker to complete the lifespan startup handshake (heartbeat).
5. Once all workers are healthy, the new master sends `SIGTERM` to the old master (read from `PAGI_MASTER_PID`).
6. The old master receives `SIGTERM`, finishes in-flight requests within its shutdown timeout, and exits cleanly.

## HUP vs USR2

```
HUP   — Rolling worker restart. Workers are replaced one by one.
         Code loaded at master startup (middleware, startup modules)
         is NOT reloaded. Use for: config changes picked up per-worker.

USR2  — Full master re-exec. Everything reloaded from disk including
         the perl binary, all modules, middleware stack. Use for:
         code deploys, Perl upgrades, PAGI::Server upgrades.
```

## Deploy Workflow

```
# Deploy new code
rsync -a ./lib/ /opt/myapp/lib/

# Hot restart (zero downtime)
kill -USR2 $(cat /var/run/myapp/pagi.pid)

# Verify (optional)
curl http://localhost:8080/health
```

## systemd Unit File

```
[Service]
Type=forking
PIDFile=/var/run/myapp/pagi.pid
ExecStart=/usr/local/bin/pagi-server \
    --host 0.0.0.0 --port 8080 \
    --workers 4 --pid /var/run/myapp/pagi.pid \
    --daemonize /opt/myapp/app.pl
ExecReload=/bin/kill -USR2 $MAINPID
KillMode=process
```

## Failure Handling

The design ensures the old master never stops until the new master explicitly sends `SIGTERM`:

* **Fork failure** — The old master logs the error and continues serving. No new master is started.
* **Exec failure** — The forked child exits before loading any code. The old master notices (via `waitpid`) and continues serving.
* **New master crash during startup** — The old master never receives `SIGTERM` and continues serving indefinitely.
* **Workers fail lifespan startup** — The new master exits without sending `SIGTERM`. The old master is unaffected.

## PERL5LIB and Module Paths

When the new master is `exec`'d it inherits the process environment, but **not** any `-I` flags that were on the original command line. If your application uses `-Ilib`, ensure `PERL5LIB` is set in the environment or in the systemd unit file so the re-exec'd process can find your modules. Alternatively, use the `--lib` flag (`pagi-server --lib ./lib ./app.pl`), which is captured in `PAGI_ARGV` and replayed on re-exec.

# WINDOWS SUPPORT

**PAGI::Server does not support Windows.**

The server relies on Unix-specific features that are not available on Windows:

* **Unix signals** - SIGTERM, SIGINT, SIGHUP for graceful shutdown and worker management
* **fork()** - Multi-worker mode requires real process forking, not thread emulation
* **IO::Async internals** - The event loop has Unix-specific optimizations

For Windows development, consider using WSL (Windows Subsystem for Linux) to run PAGI::Server in a Linux environment. The PAGI specification and middleware components can still be developed and unit-tested on Windows, but the reference server implementation requires a Unix-like operating system.

heartbeat\_timeout => $seconds
:   Worker liveness timeout in seconds. Only active in multi-worker mode (`workers >= 2`). Has no effect in single-worker mode — use `timeout` for idle connection management there.

    Each worker sends a heartbeat to the parent process via a Unix pipe at an interval of `heartbeat_timeout / 5`. The parent checks for missed heartbeats every `heartbeat_timeout / 2`. If a worker has not sent a heartbeat within `heartbeat_timeout` seconds, the parent kills it with SIGKILL and respawns a replacement.

    **What this detects:** Event loop starvation — when the worker's event loop is completely blocked and cannot process any events. This happens with blocking syscalls (`sleep()`, synchronous DNS, blocking database drivers), deadlocks, runaway CPU-bound computation, or any code that does not yield to the event loop.

    **What this does NOT detect:** Slow async operations. A request handler that does `await $db->query(...)` for 5 minutes is fine — the `await` returns control to the event loop, so heartbeats continue normally. This value should be larger than the maximum time you expect any single operation to block the event loop without yielding.

    **Default:** 50 (seconds). Set to 0 to disable.

    **Example:**

    ```
    # Tighter heartbeat for latency-sensitive service
    my $server = PAGI::Server->new(
        app               => $app,
        workers           => 4,
        heartbeat_timeout => 20,
    );

    # Disable heartbeat monitoring
    my $server = PAGI::Server->new(
        app               => $app,
        workers           => 4,
        heartbeat_timeout => 0,
    );
    ```

    **CLI:** `--heartbeat-timeout 20`

loop\_type => $backend
:   Specifies the IO::Async::Loop subclass to use when calling `run()`. This option is ignored when embedding the server in an existing loop.

    **Default:** Auto-detect (IO::Async chooses the best available backend)

    **Common values:**

    ```
    'EPoll'   - Linux epoll (recommended for Linux)
    'EV'      - libev-based (cross-platform, requires EV module)
    'Poll'    - POSIX poll() (portable fallback)
    'Select'  - select() (most portable, least scalable)
    ```

    **Example:**

    ```
    my $server = PAGI::Server->new(
        app       => $app,
        loop_type => 'EPoll',
    );
    $server->run;
    ```

    **CLI:** `--loop EPoll` (via pagi-server)

    **Note:** The specified backend module must be installed. For example, `loop_type => 'EPoll'` requires [IO::Async::Loop::EPoll](/pod/IO::Async::Loop::EPoll).

h2\_max\_concurrent\_streams => $count
:   **(Experimental - HTTP/2 support may change in future releases.)**

    Maximum number of concurrent HTTP/2 streams per connection. Each stream represents an in-flight request/response exchange. Limits resource consumption and provides protection against rapid-reset attacks.

    **Default:** 100

    This matches Apache httpd, H2O, and Hypercorn defaults. The RFC 7540 default is unlimited, but 100 is the industry consensus for a safe maximum.

    **Tuning:** Increase for API gateways handling many small concurrent requests. Decrease for memory-constrained environments or when each request is expensive.

h2\_initial\_window\_size => $bytes
:   **(Experimental)**

    Initial HTTP/2 flow control window size per stream, in bytes. Controls how much data a client can send before the server must acknowledge receipt. Also affects how much response data the server can buffer per stream before the client acknowledges.

    **Default:** 65535 (64KB minus 1, the RFC 7540 default)

    **Tuning:** Increase to 131072-262144 for high-throughput file upload/download workloads where the default window causes flow control stalls on high-latency connections. The tradeoff is higher per-stream memory usage.

h2\_max\_frame\_size => $bytes
:   **(Experimental)**

    Maximum size of a single HTTP/2 frame payload, in bytes. Must be between 16384 (16KB, the RFC minimum) and 16777215 (16MB, the RFC maximum).

    **Default:** 16384 (16KB, the RFC 7540 default)

    Most servers use the RFC default. Larger frames reduce framing overhead but increase head-of-line blocking within a stream.

h2\_enable\_push => $bool
:   **(Experimental)**

    Enable HTTP/2 server push (SETTINGS\_ENABLE\_PUSH). When enabled, the server can proactively push resources to the client before they are requested.

    **Default:** 0 (disabled)

    Server push is effectively deprecated. Chrome removed support in 2022, and nginx deprecated it in version 1.25.1. Unless you have a specific use case requiring server push, leave this disabled.

h2\_enable\_connect\_protocol => $bool
:   **(Experimental)**

    Enable the Extended CONNECT protocol (RFC 8441, SETTINGS\_ENABLE\_CONNECT\_PROTOCOL). Required for WebSocket-over-HTTP/2 tunneling.

    **Default:** 1 (enabled)

    When enabled, clients can use the Extended CONNECT method with a `:protocol` pseudo-header to establish WebSocket connections over HTTP/2 streams. Disable this only if you do not need WebSocket support over HTTP/2.

h2\_max\_header\_list\_size => $bytes
:   **(Experimental)**

    Maximum total size of the header block that the server will accept, in bytes. This is the sum of all header name lengths, value lengths, and 32-byte per-entry overhead as defined by RFC 7540 Section 6.5.2.

    **Default:** 65536 (64KB)

    Matches Hypercorn and Node.js defaults. Provides a guard against header-based memory exhaustion attacks while being generous enough for normal use including large cookies and authorization tokens.

# FILE RESPONSE STREAMING

PAGI::Server supports efficient file streaming via the `file` and `fh` keys in `http.response.body` events:

```
# Stream entire file
await $send->({
    type => 'http.response.body',
    file => '/path/to/file.mp4',
    more => 0,
});

# Stream partial file (for Range requests)
await $send->({
    type => 'http.response.body',
    file => '/path/to/file.mp4',
    offset => 1000,
    length => 5000,
    more => 0,
});

# Stream from filehandle
open my $fh, '<:raw', $file;
await $send->({
    type => 'http.response.body',
    fh => $fh,
    length => $size,
    more => 0,
});
close $fh;
```

The server streams files in 64KB chunks to avoid memory bloat. Small files (under 64KB) are read synchronously for speed; larger files use async I/O via a worker pool to avoid blocking the event loop.

## Production Recommendations for Static Files

**For production deployments, we strongly recommend delegating static file serving to a reverse proxy:**

1. **Use nginx, Apache, or a CDN**
:   Place a reverse proxy in front of PAGI::Server and let it handle static files directly. This provides:

    * Optimized file serving with kernel sendfile
    * Efficient caching and compression
    * Protection from slow client attacks
    * HTTP/2 and HTTP/3 support

2. **Use [PAGI::Middleware::XSendfile](/pod/PAGI::Middleware::XSendfile)**
:   For files that require authentication or authorization, use the XSendfile middleware to delegate file serving to the reverse proxy:

    ```
    use PAGI::Middleware::Builder;

    my $app = builder {
        enable 'XSendfile',
            type    => 'X-Accel-Redirect',  # For Nginx
            mapping => { '/var/www/protected/' => '/internal/' };
        $my_app;
    };
    ```

    See [PAGI::Middleware::XSendfile](/pod/PAGI::Middleware::XSendfile) for details.

# ENABLING TLS SUPPORT

PAGI::Server supports HTTPS/TLS connections, but requires additional modules that are not installed by default. This keeps the base installation minimal for users who don't need TLS.

## When You Need TLS

You need TLS if you want to:

* Serve HTTPS traffic directly from PAGI::Server
* Test TLS locally during development
* Use client certificate authentication

You **don't** need TLS if you:

* Use a reverse proxy (nginx, Apache) that handles TLS termination
* Only serve HTTP traffic on localhost for development
* Deploy behind a load balancer that provides TLS

**Production recommendation:** Use a reverse proxy (nginx, HAProxy, etc.) for TLS termination. They offer better performance, easier certificate management, and battle-tested security. PAGI::Server's TLS support is primarily for development and testing.

```
cpanm IO::Async::SSL IO::Socket::SSL
```

```
apt-get install libio-socket-ssl-perl
```

**Using system packages (RHEL/CentOS):**

```
yum install perl-IO-Socket-SSL
```

**Verifying installation:**

```
perl -MIO::Async::SSL -MIO::Socket::SSL -e 'print "TLS modules installed\n"'

```

# ENABLING HTTP/2 SUPPORT (EXPERIMENTAL)

**HTTP/2 support is experimental.** The API and behavior may change in future releases. Please report issues and provide feedback.

PAGI::Server provides native HTTP/2 support via the nghttp2 C library ([Net::HTTP2::nghttp2](/pod/Net::HTTP2::nghttp2)). When enabled, the server supports both TLS-based HTTP/2 (h2 via ALPN negotiation) and cleartext HTTP/2 (h2c).

## Requirements

[Net::HTTP2::nghttp2](/pod/Net::HTTP2::nghttp2) must be installed, which requires the nghttp2 C library:

```
# Install the C library
brew install nghttp2          # macOS
apt-get install libnghttp2-dev  # Debian/Ubuntu

# Install the Perl bindings
cpanm Net::HTTP2::nghttp2
```

## Enabling HTTP/2

**Via CLI (pagi-server):**

```
# HTTP/2 over TLS (recommended for production)
pagi-server --http2 --ssl-cert cert.pem --ssl-key key.pem --app myapp.pl

# HTTP/2 cleartext (h2c, for development/testing)
pagi-server --http2 --app myapp.pl
```

**Via constructor:**

```
my $server = PAGI::Server->new(
    app   => $app,
    http2 => 1,
    ssl   => { cert_file => 'cert.pem', key_file => 'key.pem' },
);
```

## How It Works

With TLS, the server advertises `h2` and `http/1.1` via ALPN during the TLS handshake. Clients that support HTTP/2 will negotiate `h2` automatically; others fall back to HTTP/1.1 transparently.

Without TLS, the server detects HTTP/2 via the client connection preface (h2c mode). HTTP/1.1 clients are handled normally.

## HTTP/2 Features

* Stream multiplexing (100 concurrent streams per connection by default)
* HPACK header compression
* Per-stream and connection-level flow control
* GOAWAY graceful session shutdown
* Stream state validation (RST\_STREAM on protocol violations)
* WebSocket over HTTP/2 via Extended CONNECT (RFC 8441)

## Conformance

Tested against h2spec (the HTTP/2 conformance test suite): **137/146 (93.8%)**. All 9 remaining failures are shared with the bare nghttp2 C library and cannot be fixed at the application level.

Load tested with h2load: 60,000 requests across 50 concurrent connections with zero failures.

See [PAGI::Server::Compliance](/pod/distribution/PAGI/lib/PAGI/Server/Compliance.pod) for full compliance details.

## Configuration

HTTP/2 protocol settings are tuned via constructor options prefixed with `h2_`. See ["CONSTRUCTOR"](#CONSTRUCTOR) for details on:

* `h2_max_concurrent_streams` - Max streams per connection (default: 100)
* `h2_initial_window_size` - Flow control window (default: 65535)
* `h2_max_frame_size` - Max frame payload (default: 16384)
* `h2_enable_push` - Server push (default: disabled)
* `h2_enable_connect_protocol` - WebSocket over HTTP/2 (default: enabled)
* `h2_max_header_list_size` - Max header block size (default: 65536)

# SIGNAL HANDLING

PAGI::Server responds to Unix signals for process management. Signal behavior differs between single-worker and multi-worker modes.

## Supported Signals

**SIGTERM** - Graceful shutdown
:   Initiates graceful shutdown. The server stops accepting new connections, waits for active requests to complete (up to `shutdown_timeout` seconds), then exits. In multi-worker mode, SIGTERM is forwarded to all workers.

    ```
    kill -TERM <pid>
    ```

**SIGINT** - Graceful shutdown (Ctrl-C)
:   Same behavior as SIGTERM. Triggered by Ctrl-C in the terminal. In multi-worker mode, the parent process catches SIGINT and coordinates shutdown of all workers to ensure proper lifespan.shutdown handling.

    ```
    kill -INT <pid>
    # or press Ctrl-C in terminal
    ```

**SIGHUP** - Graceful worker restart (multi-worker only)
:   Performs a zero-downtime worker restart by spawning new workers before terminating old ones. Useful for recycling workers to reclaim leaked memory or reset per-worker state without dropping active connections.

    **Note:** This does NOT reload application code. New workers fork from the existing parent process and inherit the same loaded code. For code deploys, perform a full server restart (SIGTERM + start).

    ```
    kill -HUP <pid>
    ```

    In single-worker mode, SIGHUP is logged but ignored (no graceful restart possible without multiple workers).

**SIGTTIN** - Increase worker count (multi-worker only)
:   Spawns an additional worker process. Use this to scale up capacity dynamically.

    ```
    kill -TTIN <pid>
    ```

**SIGTTOU** - Decrease worker count (multi-worker only)
:   Gracefully terminates one worker process. The minimum worker count is 1; sending SIGTTOU when only one worker remains has no effect.

    ```
    kill -TTOU <pid>
    ```

## Signal Handling in Multi-Worker Mode

When running with `workers => N` (where N > 1):

* Parent process manages the worker pool
* Workers handle requests; parent handles signals
* SIGTERM/SIGINT to parent triggers coordinated shutdown of all workers
* Each worker runs lifespan.shutdown before exiting
* Workers that crash are automatically respawned
* Heartbeat monitoring detects workers with blocked event loops and replaces them automatically (see `heartbeat_timeout`)

## Examples

**Zero-downtime deployment:**

```
# Deploy new code, then signal graceful restart
kill -HUP $(cat /var/run/pagi.pid)
```

**Scale workers based on load:**

```
# Add workers during peak hours
kill -TTIN $(cat /var/run/pagi.pid)
kill -TTIN $(cat /var/run/pagi.pid)

# Remove workers during quiet periods
kill -TTOU $(cat /var/run/pagi.pid)
```

**Graceful shutdown for maintenance:**

```
# Stop accepting new connections, drain existing ones
kill -TERM $(cat /var/run/pagi.pid)
```

## run

```
$server->run;
```

Standalone entry point that creates an event loop, starts the server, and runs until shutdown. This is the simplest way to run a PAGI server:

```
my $server = PAGI::Server->new(
    app  => $app,
    port => 8080,
);
$server->run;
```

For embedding in an existing IO::Async application, use the traditional pattern instead:

```
my $loop = IO::Async::Loop->new;
$loop->add($server);
$server->listen->get;
$loop->run;
```

The `run()` method handles:

* Creating the event loop (respecting `loop_type` if set)
* Adding the server to the loop
* Starting the listener
* Setting up signal handlers for graceful shutdown
* Running the event loop until shutdown

# PERFORMANCE

PAGI::Server is designed as a reference implementation prioritizing spec compliance and code clarity, yet delivers competitive performance suitable for production workloads.

## Benchmark Results

Tested on a 2.4 GHz 8-Core Intel Core i9 Mac with 8 workers, using [hey](https://github.com/rakyll/hey) against a PAGI hello world application:

**Peak Performance (100 concurrent, 10 seconds):**

```
----------------------------------------------------------------

/html           10,932      8.4ms    19.3ms   143 bytes
/json           9,806       8.8ms    28.2ms   50 bytes
/greet/:name    10,722      8.9ms    15.4ms   17 bytes (path params)
```

**Concurrency Scaling:**

```

-----------------------------------------
10            9,757       0.9ms     2.1ms
100           12,100      7.8ms     14.1ms
500           11,299      43.3ms    63.7ms
```

**Sustained Load (30 seconds, 200 concurrent):**

```

Total requests:  298,171
Latency p99:     39.5ms

```

## Comparison

```
Server                  Req/sec     p99 Latency   Notes
---------------------------------------------------------------
PAGI (8 workers)        10-12k      13-40ms       Async, zero errors
Uvicorn (Python)        10-15k      varies        ASGI reference
Hypercorn (Python)      8-12k       varies        ASGI
Starman (Perl)          8-10k       2-3ms*        Sync prefork

* Starman shows lower latency at low concurrency but experiences
  request timeouts under high concurrent load (500+ connections)
  due to its synchronous prefork model.
```

## Key Findings

* **Keep-alive is essential** - Without it, throughput drops 6x and port exhaustion errors occur under load.
* **Zero errors under sustained load** - 298k requests over 30 seconds with no failures when using keep-alive connections.
* **Consistent tail latency** - p99 is typically only 2x p50, indicating predictable performance without major outliers.
* **JSON overhead** - JSON serialization adds ~20% overhead vs plain text.

PAGI's async architecture handles high concurrency gracefully without queueing or timeouts, making it well-suited for WebSocket, SSE, and bursty traffic patterns that would overwhelm traditional prefork servers.

## Worker Tuning

For optimal performance, set `workers` equal to your CPU core count:

```
# Recommended production configuration
my $server = PAGI::Server->new(
    app     => $app,
    workers => 16,  # Set to number of CPU cores
);
```

Guidelines:

* **CPU-bound workloads**: workers = CPU cores
* **I/O-bound workloads**: workers = 2 × CPU cores
* **Development**: workers = 0 (single process)

Exceeding 2× CPU cores typically degrades performance due to context switching overhead.

## System Tuning

For high-concurrency production deployments, ensure adequate system limits:

```
# File descriptors (run before starting server)
ulimit -n 65536

# Listen backlog (Linux)
sudo sysctl -w net.core.somaxconn=2048

# Listen backlog (macOS)
sudo sysctl -w kern.ipc.somaxconn=2048
```

PAGI::Server defaults to a listen backlog of 2048, matching Uvicorn's default. This can be adjusted via the `listen_backlog` option.

## Event Loop Selection

PAGI::Server works with any [IO::Async](/pod/IO::Async) compatible event loop. If you are on Linux, its recommended to install [IO::Async::Loop::EPoll](/pod/IO::Async::Loop::EPoll) because that is the best choice for Linux and if installed will be automatically used.

For other systems I recommend testing the various backend loop options and find what works best. Your notes and updates appreciated.

# ACCESS LOG FORMAT

The `access_log_format` option accepts Apache-style format strings or preset names. Format strings are pre-compiled into closures at server startup for fast per-request formatting.

## Format Atoms

`%h` - Client IP address


`%l` - Remote logname (always `-`)


`%u` - Remote user (always `-`)


`%t` - CLF timestamp (e.g., `10/Feb/2026:12:34:56 +0000`)


`%r` - Request line (e.g., `GET /path?query HTTP/1.1`)


`%m` - Request method


`%U` - URL path (without query string)


`%q` - Query string (with leading `?`, or empty)


`%H` - Protocol (e.g., `HTTP/1.1`)


`%s` - Response status code


`%b` - Response body size in bytes (`-` if zero)


`%B` - Response body size in bytes (`0` if zero)


`%d` - Duration in seconds with 3 decimal places (e.g., `0.123`)


`%D` - Duration in microseconds (integer)


`%T` - Duration in seconds (integer)


`%{Header}i` - Value of request header (case-insensitive, `-` if missing)


`%%` - Literal percent sign

## Named Presets

`clf` (default)
:   `%h - - [%t] "%m %U%q" %s %ds` - PAGI's default format with fractional second duration.

`combined`
:   `%h - - [%t] "%r" %s %b "%{Referer}i" "%{User-Agent}i"` - Apache combined format with referrer and user agent.

`common`
:   `%h - - [%t] "%r" %s %b` - Apache common log format with response size.

`tiny`
:   `%m %U%q %s %Dms` - Minimal format showing method, path, status, and duration in milliseconds.

# LOOP INTEROPERABILITY

PAGI::Server uses [IO::Async](/pod/IO::Async) as its event loop. When using `pagi-server` (the CLI), if [Future::IO](/pod/Future::IO) is installed, it is automatically configured to use the IO::Async backend. This enables seamless integration with Future::IO-based libraries like [Async::Redis](/pod/Async::Redis).

## Programmatic Usage

If you're using PAGI::Server programmatically (embedding it in your own script rather than using pagi-server), you must configure Future::IO yourself before loading any Future::IO-based libraries:

```
#!/usr/bin/env perl
use strict;
use warnings;
use IO::Async::Loop;
use PAGI::Server;

# Configure Future::IO BEFORE loading Future::IO-based libraries
use Future::IO::Impl::IOAsync;

# Now Future::IO libraries work correctly
use Async::Redis;

my $app = sub { ... };

my $loop = IO::Async::Loop->new;
my $server = PAGI::Server->new(
    app  => $app,
    port => 8080,
);

$loop->add($server);
$server->listen->get;
$loop->run;
```

## Why This Matters

[Future::IO](/pod/Future::IO) provides event loop-agnostic async I/O operations (sleep, read, write). Libraries built on Future::IO can work with any event loop, but Future::IO must be told which backend to use.

When using `pagi-server`, this is handled automatically. When embedding PAGI::Server, you control the setup and must configure Future::IO explicitly if you use libraries that depend on it.

Features that require Future::IO configuration:

* ["every" in PAGI::SSE](/pod/PAGI::SSE#every) - Periodic SSE events
* [Async::Redis](/pod/Async::Redis) - Redis client
* Other Future::IO-based libraries

If Future::IO is not configured, these features will fail with a helpful error message explaining how to fix it.
