# 📖 企业级 LLM Agent 实践指南

## 💡 核心导言：业务因果链与架构主权
在生产环境中，盲目堆砌 Agent 框架（如 LangGraph、AutoGen、CrewAI）往往是灾难的开始。技术选型的第一性原理是**业务因果链优先**：明确系统输入输出边界、失败后的状态落点，以及谁为副作用买单 [1]。自研或深改框架的核心目的在于掌控数据路径、对齐内部权限、建立评测闭环，让系统实现“越用越聪明”的数据飞轮 [2, 3]。

## 维度一：Agent 架构与流程编排

### 1. LangGraph：超越线性 Pipeline 的人机协同引擎
图框架的核心价值不在于跑通线性流程，而在于管理**复杂的副作用边界**和**状态演化** [2]。在真实的业务链条中，由于工具返回结果的不可预见性，我们需要“分支+状态+可持久化”的基础设施。

*   **可重放的状态机快照（Checkpoint）**：Checkpoint 绝非简单的“存档”，它是 Agent 在特定时刻执行轨迹的**绝对事实快照** [4, 5]。它记录了当前已提交的状态和尚未完成的副作用边界。在生产中，必须将“图的执行 ID（Thread ID）”与“业务领域主键（如订单号）”分离，并利用业务键保证恢复时的幂等性 [4, 5]。
*   **中断（Interrupt）的作用**：Interrupt 充当了软件定义的断点，是**人机协同的挂起点** [5-7]。当 Agent 遇到高风险操作（如发邮件、扣款）或缺乏关键信息时，Interrupt 会将当前飞行状态（in-flight state）序列化至数据库（如 PostgresSaver），并交出控制权 [6, 8]。恢复时，系统能够基于 Checkpoint 重新唤醒执行 [6]。

### 2. 状态演化策略（Reducer）在并发中的意义
在并发执行（并行节点）下，多个节点可能同时尝试修改同一个状态字段。若没有约束，这会导致严重的竞态条件和数据覆盖 [9, 10]。
*   **Reducer 的本质**：Reducer 并非单纯的语法糖，而是规定了**并发状态合并的语义契约** [5, 11]。它必须满足结合律（Batching-invariance） [9]。
*   **解决方案**：例如处理消息列表时，使用 `add_messages` 进行合并去重，而不是暴力的覆盖 [10, 11]。如果开发者不定义明确的 Reducer 策略（如 append-only 或 merge），几个月后这张“图”就会变成无人敢动的黑箱 [5]。

### 3. ReAct vs. Plan-Execute 的成本与可修正性
在面试和实践中，两者的区别远不止于“先想再做” [12]。
*   **ReAct（推理与行动交织）**：适用于探索路径不可预见、反馈密集的**部分可观测环境** [12, 13]。**难题**：容易陷入“死循环（Doom loops）”和指令遗忘 [13, 14]。**解法**：需引入中间件追踪执行频率，设置 Wall-clock 超时，以及基于语义重复度的检测 [15, 16]。
*   **Plan-Execute（计划与执行分离）**：适用于步骤可枚举、工具调用昂贵的长周期任务 [12, 13]。**优势**：在计划阶段可以引入人工确认；执行器只需要局部指令，极大提升了**Token效率（成本低）**并降低了错误级联的概率 [13]。**难点**：计划一旦出错，谁来修正？必须设计局部重规划（Re-plan）机制和执行期的异常熔断 [12, 13]。

## 维度二：长期记忆与上下文管理

### 1. 应对事实漂移（Fact Drift）与模型幻觉
在长对话中，随着上下文的滚动，早期的硬约束往往会被淹没在工具调用的噪声中，导致 **事实漂移（Fact Drift）** [17, 18]。模型可能会产生幻觉，因为最新提取的工具日志覆盖了用户的原始意图 [19]。
*   **解决方案**：引入 **ACC（Agent Cognitive Compressor，智能体认知压缩器）** 或显式指令锚点。ACC 不再无脑附加聊天记录，而是在每个轮次计算一个**有界的压缩认知状态 (CCS)** [20]。另外，将原始目标作为“系统级锚点（System Anchor）”置于每个 Prompt 的顶部，而非随对话流滚动，能有效减少 60% 的漂移 [21, 22]。

### 2. 划定“图内State”与“外置记忆”的边界
Checkpoint 膨胀会拖垮数据库性能并耗尽 Token [20, 23]。必须实施严格的边界划分：
*   **图内 State（Working Memory）**：只保留当前任务推进必需的数据——如最近 3-5 轮对话、标志位、未完成的工具结果。任务结束后清空或过期 [23, 24]。
*   **外置记忆（Long-term Semantic Memory）**：跨 Session 的用户偏好、结论沉淀至外置向量库或关系型数据库中 [23, 25]。

### 3. 上下文路由、时间戳校验与外置真相源
记忆不是“记下就好”，关键在于“记对”并能防篡改：
*   **上下文路由（Context Routing）**：不同子任务动态挂载不同的记忆窗口，避免无用历史注入 [26]。
*   **时间戳校验与外置真相源**：长期记忆必须具备时间戳、置信度和溯源链接。在读取时，拦截器需将记忆片段与外部真相源（如业务主库、交易流水）对比，以校验是否过期。一旦冲突，以外置 DB 为准，拒绝因对话产生的虚假历史 [23, 27]。

## 维度三：工具链（Tools）、Skill 与协议

### 1. Tool 与 Skill 的本质区别与分工
*   **Tool（原子能力）**：是无状态的、低级执行接口（如查询数据库、调用 REST API），它们只定义“能做什么”（What） [28-30]。
*   **Skill（可版本化工作说明）**：是高阶的、带有观点的业务流程说明书（Recipe Cards）。它包含执行步骤、已知良好结果、安全护栏以及少量入口工具的挂载 [16, 29, 31]。将复杂逻辑 Skill 化，是为了把“高频任务的打法”变成可测试、可迭代的资产 [32]。

### 2. MCP（Model Context Protocol）的传输契约
MCP 解决了 Agent 与外部异构系统集成的 N x M 难题，它本质上是**宿主与能力之间的传输与描述契约** [16, 33]。
*   **作用**：它将外部 API 抽象为 LLM 可理解的 JSON-RPC 格式，处理身份验证（Token 派发），并提供进程隔离（防止恶意代码直接攻击宿主 Agent） [34, 35]。
*   **争议点**：MCP 服务器若直接加载，会导致所有 Tool Schema 被注入 Context，瞬间吞噬数万 Token [36, 37]。

### 3. 大规模工具集成：发现、加载与幂等性
当工具扩展到成百上千个时，一次性加载不可行：
*   **检索式 Tool Selection**：动态发现工具。系统初始只暴露一个“搜索工具”和核心 Tool。模型需要能力时，通过检索召回 Top-K 的 Schema 再注入当前上下文 [38]。
*   **权限裁剪（RBAC）**：在 Schema 下发阶段，Gateway 必须校验用户的 OAuth 凭证，动态裁剪越权工具 [16, 38]。
*   **重试风暴与幂等性**：API 限流可能导致模型疯狂重试（Retry Storm） [39]。架构上必须要求所有写操作工具携带**业务幂等键（Idempotency Keys）**，数据库查询工具在驱动层强制开启 Read-Only 约束，防范 Prompt 注入导致的删库风险 [16, 40]。

## 维度四：高级 RAG（检索增强生成）系统构建

### 1. 检索策略原理与适用场景对比
在 RAG 中，“Chunk 切分即命运” [41]。
*   **混合检索（Hybrid Search）**：结合 Dense Vector（查语义）与 BM25（查确切术语），通过 RRF（Reciprocal Rank Fusion）合并。适用：企业异构文档库，能大幅提升召回率 [42, 43]。
*   **多路召回（Multi-query）**：利用大模型将用户原始 Query 改写为 3-5 种变体并发检索。适用：用户提问表述与文档术语存在Gap的场景 [44]。
*   **HyDE（假设性文档嵌入）**：让大模型先生成一个“伪答案”，拿伪答案去向量搜索。适用：简短且缺乏上下文的口语化查询，大幅提升语义对齐度 [45]。
*   **Parent-child Chunking（父子分块）**：切分粒度两极分化。子 Chunk 极小，保证召回的精准度；父 Chunk 较大，在返回给 LLM 时替换子 Chunk 以提供充足的上下文 [46-48]。

### 2. Cross-encoder Reranker 的排序优势
粗筛（ANN 检索）往往只反映向量距离，不代表真正的业务相关性。
*   **为什么不用生成模型排序**：让大模型（如 GPT-4）对上千个候选直接排序既昂贵又存在注意力丢失 [49, 50]。
*   **Cross-encoder 优势**：它将 Query 和 Document 拼接在一起同时输入，允许模型内部进行深度的全交叉注意力交互（Cross-attention），从而精准捕捉由于极其细微的用词差异带来的逻辑否定 [51-53]。这能过滤掉仅有相关关键词但无法回答问题的噪音块。

### 3. 引用追踪（Citations）与拒答机制
“能搜到不代表敢直接用”，企业级 RAG 需要刚性的控制：
*   **引用追踪（Citations）**：从 Ingestion 阶段起，必须为每个 Chunk 植入元数据（URL、Offset、作者）。生成阶段在 Prompt 中强制约束模型输出时附带括号引用的 Index（如 `[54]`） [55, 56]。
*   **拒答机制（Abstention/No-Answer）**：应对幻觉的核心手段。通过 Prompt 约束如果检索内容不含答案，必须标准化返回“我没有足够信息”。在工程链路上，常通过 NLI（自然语言推理）分类器在后处理阶段，比对生成结果与检索文本的逻辑蕴含关系，一旦无法溯源直接熔断拒答 [55]。

## 维度五：Agent 后端基建与高可用工程

大语言模型带来的长耗时特性，对传统 Web 后端是巨大的冲击，必须基于常驻长连接和异步框架进行改造 [57]。

### 1. 流式响应技术细节 (SSE)
*   **Server-Sent Events (SSE)**：LLM 吐字（Token Streaming）的标准协议。它是单向的长连接，基于 `Content-Type: text/event-stream` 与 Chunked 传输 [58, 59]。
*   **基建坑点**：如果使用了 Nginx 或任何负载均衡器，必须强制配置 `proxy_buffering off` 以及 `X-Accel-Buffering: no`，否则 Token 会被网关拦截缓存，用户端会看到长时间卡顿后一次性蹦出结果 [59, 60]。
*   **注释心跳保活**：由于生成推理可能存在卡顿，后端必须定期向连接注入空的注释行（如 `: heartbeat`）来重置网关的空闲连接超时器（Idle timeout） [57, 60]。在多设备同步断线场景下，应向 **Durable Sessions（持久化会话机制）** 演进，通过 offset 实现断线续传 [61, 62]。

### 2. 大文件上传与流式解析的异步工程链路
在 Agent 接收代码库、海量 PDF 时的规范链路 [57, 62, 63]：
*   **断点校验与上传分片**：客户端采用分块（Chunked）上传，每个块附带 MD5 checksum，由 Ingress 层非对称计算以防重传和网络损坏 [63]。
*   **背压与限流**：Ingress API 检测到解析集群过载时，通过 Backpressure（背压）通知客户端降速，保证主链路不雪崩 [57, 63]。
*   **MQ 解耦**：收到完整文件后不直接在 Web 请求内解析。生成一个 Task ID 响应给前端，并将实际解析任务丢入 RabbitMQ 或 Kafka 中进行异步解耦 [57, 63]。
*   **流式解析（Stream Parsing）**：绝对禁止将大文件一次性 Load 进内存（容易 OOM）。Worker 消费时通过迭代器惰性读取（mmap / sendfile），生成 Markdown 后实时灌入向量数据库，并记录审计日志 [57, 63]。

---
**结语：** 卓越的 Agent 绝不是写一段神奇的 Prompt，而是架构在可观测平台（LangSmith/Langfuse）、强健的并发状态机、防御性代码边界，以及以执行轨迹（Traces）为基石的评测台（Agentic Harness Engineering）之上的工程系统 [3, 64, 65]。只有让每一个故障都有据可查，每一次回滚都从容不迫，AI 才能真正承担企业级业务的重托。
